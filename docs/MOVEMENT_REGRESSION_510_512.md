# Остановка юнитов: сравнение 510 и 512

Последующее уточнение: среди семи независимых откатов коммитов 510 → 511 пользователь нашёл работающий вариант `03_fec12de`. В нём движение восстановлено и без ботов, и с ботами. Связь регрессии с `fec12de` подтверждена этим игровым сравнением; точная часть коммита пока проверяется. См. [полный разбор fec12de](FEC12DE_MOVEMENT_INVESTIGATION.md). Остальной текст ниже описывает более ранний этап исследования.

Проверка 2026-10-13. Сравниваются архивы в корне проекта:
`23_Race_Legion_v1_6_510.w3x` и `23_race_1_6_512.w3x`.
Архив 512 и текущая распакованная карта — разные снимки: в рабочей карте есть
последующие изменения. Выводы ниже относятся именно к двум архивам.

## Подтверждено

- Игрок сообщает, что собственные юниты не двигаются сразу, войска ботов — позже.
- Проверены все файлы из MPQ listfile: 5185 в 510, 5187 в 512.
- Побайтово одинаковы `war3map.wpm`, `war3map.w3e`, `war3map.doo`,
  `war3mapUnits.doo`, object data декораций/разрушаемых объектов,
  `war3mapMisc.txt`, импортированные модели и текстуры.
- Различия unit object data: требования исследования Древа войны, способности
  двух форм друида-совы, поля строительства зданий Наг и трёх зданий Альянса.
  Общего изменения скорости/столкновений мобильных юнитов нет.
- Единственное различие ability object data — `A0EF.areq = R0LC`.
- В изменённых строках скрипта нет новых общих вызовов `PauseUnit`,
  `SetUnitMoveSpeed`, `SetUnitPathing`, `SetTerrainPathable`.
  Новый `stop` относится только к рывку Лунного воина с исследованием `R0LC`.

Это исключает изменение сохранённой сетки проходимости и размещения объектов
между архивами как объяснение регрессии. Не исключены препятствия и столкновения,
создаваемые во время игры, либо ошибка движка при инициализации/поиске пути.
Причина пока не установлена; исправление игрового поведения не вносилось.

Предыдущее наблюдение в рабочей 512: приказ рабочего принимался при нормальной
скорости, наличии `Amov` и отсутствии паузы; временное отключение pathing позволяло
двигаться. См. [AI_OVERHAUL_PLAN.md](AI_OVERHAUL_PLAN.md).
Это наблюдение не является сравнительным игровым тестом двух архивов.

## Артефакты

Локальные результаты в `.cache/wc3/`:

- `version-comparison.json`: размеры и SHA256 основных файлов.
- `510-512-all-files.json`: полный список различий файлов архивов с SHA256.
- `510-512-script.diff`: изменения Lua-скрипта.
- `compare-510/`, `compare-512/`: извлечённые основные файлы.

Первый запуск архивной 512 через `probe-map` остановился на экране входа Battle.net.
После самостоятельной загрузки игроком мост заработал и проблема воспроизведена.

## Игровые наблюдения в архивной 512

Проверялись работники Альянса около `(-3632, 29264)` в Нордсколе.
Наличие новых боевых функций рабочей ветки не обнаружено (`AiCombatTick == nil`),
поэтому эти результаты не приписываются текущему изменённому Lua-скрипту.

- Скорость 190, `Amov = 1`, `paused = false`, радиус столкновения 12.
- `move` принимается (`851986`), затем ордер становится 0 без достижения цели.
- Работник без pathing прошёл от `(-3664, 29264)` до `(-3989.246, 29264.02)`;
  через три секунды pathing автоматически восстановлен. Обычный следующий приказ
  снова не привёл к движению.
- Грифон прошёл примерно 392 единицы с включённым обычным pathing.
- Свежие наземные юниты также застревали. Проба в тестовой области
  `(28400, -27856)` закончилась смещением лишь примерно 18 единиц.
- Перехват приказов увидел только выданный `move`; перехват `SetUnitPosition`
  не обнаружил возврата проверяемого работника скриптом.
- На три секунды отключены 1027 включённых глобальных `gg_trg_*`; работник
  не сдвинулся. Триггеры автоматически возвращены в исходное состояние.
  Свежий работник, созданный в этом окне, тоже не пошёл.
- Ближайшие разрушаемые объекты и здания не объяснили остановку во всех
  проверенных точках. Перечисление групп не гарантирует обнаружения Locust-юнитов.
- Статический маршрут от `(-3989, 29264)` до `(-4400, 29264)` доступен даже
  с наложением исходных footprints декораций через `wc3_pathing.py`.
- Игрок также показал красные клетки размещения здания без видимого препятствия.
  Проверка соответствующих buildability-клеток пока не завершена.

Отключение триггеров исключает их активное вмешательство в течение пробы, но
не исключает препятствие или повреждённое состояние, возникшее раньше.
Контрольный игровой запуск 510 ещё не выполнен. Это не подтверждение причины.

После переключения к аудиту мост перестал отвечать. Восстановление временно
отключённых триггеров и pathing подтверждено ранее; финальное удаление восьми
тестовых юнитов и возврат проверенного работника на исходную точку пока не
подтверждены. Команда уборки опубликована в ожидаемом inbox `seq=39` и может
выполниться при возобновлении этой сессии. Перед новым запуском карты требуется
обычный `agent_bridge.py reset` при закрытой игре, чтобы старые команды не
переигрывались.

## Аудит изменённого кода

Извлечены split-источники из обоих архивов. Их конкатенация по manifest **точно
совпадает** с соответствующим архивным `war3map.lua`. Найдено 4796 именованных
функций в 510 и 4807 в 512; различаются 298 функций. В 51 изменённой функции
есть операции с юнитами/препятствиями/перемещением. Само наличие такой операции
не означает, что она изменилась: например, могли исправить только путь эффекта.

Количество прямых записанных вызовов в исходнике, не число объектов в игре:

| Операция | 510 | 512 |
|---|---:|---:|
| `BlzCreateUnitWithSkin` в исходном размещении | 621 | 621 |
| `CreateUnit` | 46 | 67 |
| `CreateUnitAtLoc` | 30 | 30 |
| `CreateNUnitsAtLoc` | 209 | 187 |
| `CreateDestructableLoc` | 8 | 0 |
| `CreateDestructable` | 0 | 8 |
| `SetTerrainPathable` | 0 | 0 |
| `SetUnitPathing` | 11 | 11 |
| `PauseUnit` / `PauseUnitBJ` | 12 / 8 | 12 / 8 |
| `SetUnitMoveSpeed` | 6 | 6 |

Переход на `CreateUnit` в основном заменяет старые GUI-вызовы, а не добавляет
новые типы объектов. Полный файл исходного размещения `120_unit_creation.lua`,
`CreateRegions`, обычный выбор расы в `04_race_selection.lua` по коду и
`RunInitializationTriggers` не изменены.

### Изменения, способные косвенно затронуть старт

1. **Перенос создания глобальных handles** из корневых объявлений в
   `Global___Init` и `InitGlobals`: группы, силы, region, timers, temporary loc/rect.
   Новый ранний вызов `SetPortalGroup` создаёт по три группы для каждого игрока.
   Эти handles не являются физическими юнитами или blockers. Изменился порядок
   доступности общих групп/регионов для стартовых обработчиков — это отдельный
   кандидат для сравнения инициализации, а не установленная причина.
2. **`CachedFilter` вместо голых функций** в ряде `GroupEnum*`. Исправленная форма
   фильтра может начать выполнять прежнюю ветку, которая в 510 не работала.
   Нужен журнал фактических `CreateUnit`/`BlzCreateUnitWithSkin`/`CreateDestructable`
   с начала карты; отключение триггеров после появления проблемы этого не проверяет.
3. **`ForGroupDestroy` вместо `ForGroupBJ`** освобождает свежие группы.
   Физические объекты эта функция не создаёт. Проверять следует конкретный
   callback и владение переданной группой, а не предполагать общий blocker.
4. **`aiStart`** теперь использует локальный `pi` вместо общего `gInt`.
   Это меняет надёжность запуска компьютерных слотов. При наличии ботов стоит
   сравнить фактическое число запущенных AI и объектов; само по себе не объясняет
   одиночных стартовых работников при отсутствии ботов.
5. **Новые триггеры NightElf**: Ignite и друид-совa работают с уроном,
   способностями и эффектами; Crescent Dance двигает только атакующего Лунного
   воина с `A0EF` и исследованием `R0LC`. Новых физических объектов здесь нет.

### Object data, влияющие на проходимость

Всего 47 различий полей в `w3u`/`w3a`/`w3q`, включая добавленный `R0LC`.
Прямые изменения footprint/placement/movement:

- Базовые `nnad`, `nnfm`, `nnsa`, `nnsg`, `nntg`, `nntt`:
  добавлены пустые `umvt`/`upar`, у ряда зданий `upap = unwalkable`.
- `nntg.upat` явно задан как `PathTextures\\4x4SimpleSolid.tga`.
- `n04L.umvt`: `float` → пусто; `upap`: `unfloat` → `unwalkable`.
- `n055`: добавлены аналогичные сухопутные поля.
- `h0JW`, `h0JX`, `h0JY`: добавлены пустые `umvt`/`upar`.

Проверка 621 исходного `BlzCreateUnitWithSkin` не нашла размещённых экземпляров
перечисленных баз Наг либо их custom-потомков. Эти правки могут влиять на
создаваемые здания Наг, но их связь с остановкой работников Альянса сразу после
выбора расы не подтверждена. Worker `hpea` и обычный `hfoo` не менялись.

### Следующий порядок поиска причины

Наиболее полезен контроль двух независимых частей: **скрипт 510 + object data 512**
и **скрипт 512 + object data 510**, при одинаковом ландшафте и начальных объектах.
Это диагностические копии; основную карту пока не менять. Такой контроль
покажет, искать ли причину в инициализации/фильтрах либо в object data/движке.
Если подтвердится скрипт, отдельно проверять перенос глобальных handles,
старые callbacks, активированные `CachedFilter`, и создание/удаление `n04G`.

Новый безусловный код, создающий скрытые blockers возле всех работников,
аудитом **не найден**. Это не исключает косвенное выполнение прежнего кода.
Отмена перечисленных правок без контрольного теста пока не обоснована.

## Следующее измерение в игре

В одиночной загруженной карте включить `-bridge:eval:on`. Пока застрявший юнит
имеет приказ движения, дважды с интервалом несколько секунд выполнить:

```powershell
python agent_bridge.py exec --file tests/live_movement_snapshot.lua
```

По умолчанию проверяется игрок 0, рабочие и герои идут первыми. Для бота:

```powershell
python agent_bridge.py exec "MovementProbeSlot=2; MovementProbeUnit=nil"
python agent_bridge.py exec --file tests/live_movement_snapshot.lua
```

Скрипт только читает состояние: ордер, координаты, смещение между снимками,
скорость, паузу, `Amov`, радиус столкновения, соседние юниты/здания,
разрушаемые объекты и девять точек проходимости. Собственные временные группа и
прямоугольник уничтожаются. Приказы и pathing не изменяются.

Снимки нужны в обеих версиях у одного типа юнита и одних координат. После этого
можно изолировать ближайшее препятствие или конкретный триггер и проверить
причину повторным измерением, прежде чем менять исходники карты.
