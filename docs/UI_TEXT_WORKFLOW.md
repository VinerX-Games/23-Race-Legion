# Экономный порядок работы с игровыми текстами

Этот порядок дополняет [стандарт текстов](UI_TEXT_STYLE.md), [палитру](UI_COLOR_PALETTE.md) и [TODO](UI_TEXT_TODO.md). Экономия достигается ограничением повторной работы и вывода, при сохранении требований к полноте и достоверности текста.

## Границы задачи

- В начале зафиксировать расу/систему, категории, объекты или источник их списка, требуемый результат и проверки. Сохранять исходную цель пользователя; рабочая порция не заменяет всю задачу.
- Включать прямую зависимость, если без неё описание выбранного объекта останется неверным или неполным: например, способность героя или исследование из меню здания. Общий объект сам по себе не означает необходимость переработать все использующие его расы и подсистемы.
- При изменении общей строки проверить её непосредственных потребителей и совместимость формулировки. Не обходить рекурсивно их полные деревья технологий без конкретной необходимости.
- Найденные посторонние ошибки механики и тексты вне исходного охвата записывать кратко в остаток. Не исправлять их попутно. Если общая система явно входит в исходную задачу, выполнить её в рамках этой задачи.
- Не запускать игровой клиент, если пользователь оставил игровые проверки себе. Отмечать их владельца и не использовать такие проверки как основание для бесконечного продолжения статической задачи.

## Чтение и исследование

- При продолжении прочитать контрольную запись задачи и нужный раздел TODO, затем проверить текущие изменяемые файлы. Не перечитывать всю историю, все реестры и всю документацию проекта.
- Искать сначала через `rg`; читать конкретные функции и поля. Независимые чтения объединять в один вызов инструментов.
- Получать данные пакетно по списку rawcode и необходимых полей, сразу со всеми действующими уровнями и SD/HD. Повторно читать только изменившиеся или противоречивые данные.
- Полные выгрузки сохранять в файл; в контекст выводить количества, существенные различия и ошибки. Ограничение вывода не считать ограничением проверяемого набора. У native HiveWE `dump-objects` полноту задаёт `--max`; `--limit` другого режима может ограничивать только отображение или не управлять этой командой. Проверять фактическое число возвращённых объектов.
- Источники механики изучать до уровня, достаточного для точной формулировки. Проверенные сведения переиспользовать, пока соответствующие данные/код не изменились. Новое расследование обосновывать конкретным пробелом или противоречием.
- Не придумывать числа и эффекты ради сокращения исследования. Если факт не установлен, записать точный вопрос и источник; явно отделить незавершённый текст от известной посторонней ошибки механики.

## Пакет правок и проверки

1. Собрать одну содержательную порцию: категория расы или явно входящая в задачу общая система. Подготовить тексты и связанные ссылки вместе.
2. Применить пакет через существующий инструмент. Не создавать отдельный почти одинаковый скрипт, план, отчёт и тест для каждого объекта; предпочитать общий инструмент и один реестр задачи. Сохранять уже существующие артефакты, если они нужны для восстановления или проверки.
3. Один раз проверить результат после записи: точное чтение изменённых текстов SD/HD или WTS, метки, палитру, сбросы, клавиши и сохранность нетекстовых данных. Ссылаться на отчёт вместо его повторного вывода.
4. Выбирать остальные проверки по изменённым источникам. Для markdown достаточно diff и локальных ссылок; для WTS/object data — проверки соответствующих данных; для Lua — сборка и необходимые регрессии. Полный `verify` выполнять при сдаче изменений Lua, а не после каждой текстовой порции.
5. Повторять успешную проверку только после изменения её входных файлов, ошибки предыдущего запуска или появления конкретного нового риска. Общий проверочный отчёт в конце задачи запускать один раз для актуального состояния.

Прежние замечания валидатора сравнивать с сохранённым списком, а не только с его размером. Не расследовать их заново в каждой порции и не запускать повторно полный набор тестов ради прежнего предупреждения. Новые ошибки проверять и устранять в пределах задачи; исключения не скрывать ради зелёного отчёта.

## Передача состояния и завершение

В TODO хранить одну актуальную контрольную запись; журнал — одна короткая запись на содержательную порцию. Не наращивать повторяющиеся пересказы и не дублировать полные выгрузки в markdown.

Формат контрольной записи:

```text
Статус: активна / приостановлена пользователем / завершена.
Охват: раса/система, категории, ссылка на реестр.
Сделано: результат и изменённые источники, без истории попыток.
Проверено: команды, результат, ссылка на отчёт и состояние проверенных файлов.
Осталось: конечный список конкретных работ или вопросов.
Следующий шаг: одно действие; повторно не делать: уже закрытые исследования/проверки.
Игровые проверки: агент / пользователь; влияние на условия завершения.
```

Для новой сессии достаточно этой записи и ссылок на источники. При желании пользователь задаёт явный бюджет токенов; не создавать бюджет или менять цель без такого указания.

Перед завершением один раз сопоставить исходный охват с реестром, текущими файлами и подходящими отчётами. Не объявлять весь объём готовым по частичной проверке. После доказанной полноты не начинать новый общий аудит без новых оснований. Незавершённые обязательные пункты назвать прямо; переданные пользователю игровые проверки не выдавать за выполненные агентом.
