# План улучшения инструментов разработки карты

Результат внедрения и оставшиеся ограничения: [TOOLING_IMPLEMENTATION.md](TOOLING_IMPLEMENTATION.md).
Рабочие команды: [TOOLING_WORKFLOW.md](TOOLING_WORKFLOW.md). Ниже сохранён исходный анализ до изменений.

Дата анализа: 2026-10-12. Проверены split-исходники, сборщик, Python-обёртки, шесть локальных скиллов, тесты, аудиторы и справка установленного HiveWE CLI. Ниже отделены подтверждённые дефекты от предлагаемых возможностей. Игровые запуски не выполнялись; исходный код HiveWE не исследован.

Запуск текущего `python scripts/wc3_tools.py verify`: синхронизация сборки, Lua-синтаксис и unittest прошли; валидатор AI вернул замечания, но общий процесс завершился с кодом 0. Замечания валидатора включают legacy-хуки, поэтому их нельзя автоматически считать игровыми багами: сначала нужна классификация severity.

## Главный вывод

Максимальную пользу сейчас даст исправление существующих инструментов и объединение их в проверяемый рабочий цикл. Дополнительные скиллы полезны как короткие инструкции к этому циклу. Внешний плагин пока не требуется: доступ к локальным данным карты, движку Lua, HiveWE и мосту уже есть.

## Подтверждённые проблемы

1. **Недостоверный статус проверки.** `scripts/wc3_tools.py::cmd_verify` заканчивается `return 0` независимо от ошибок синтаксиса, рассинхронизации, валидатора и тестов. `build_map_lua.py --check-only` тоже возвращает 0 при несовпадении хешей. Нужны ненулевые коды ошибок и явное разделение обязательных проверок и предупреждений.
2. **Неверный маппинг строк.** `get_sections_info` суммирует количество `splitlines()` по файлам, а сборщик конкатенирует текст без разделителя. Некоторые секции не заканчиваются переводом строки. При сравнении с фактической конкатенацией начальная строка неверна у 128 из 147 секций. Например, начало `80_runtime/_infra/30_player_counter.lua`: инструмент вычисляет 9875, фактическое значение 9874. Следует считать реальные символьные смещения/переводы строк и сохранять карту исходников вместе с хешем сборки. Строка на границе может принадлежать двум секциям; это нужно учитывать.
3. **Поиск HiveWE теряет результаты.** CLI `search-objects` возвращает `matches`, Python-обёртка читает `results` или `objects`. Запрос `Работник` с лимитом 2 напрямую вернул два объекта, через обёртку — «No objects found». Нужны нормализация схемы и тест контракта.
4. **Проверка рас отличается от сборки.** Валидатор читает `82_ai_races/*.lua` через `glob`, сборщик — manifest. Не включённый в сборку файл может попасть в проверку. Пути валидатора зависят от текущего каталога. Использовать общий загрузчик manifest и корень относительно `__file__`.
5. **Smoke-проверки могут печатать ошибки без падения.** `tests/test_lobby_smoke.py` исполняет сценарий при импорте, без `unittest.TestCase` и assertions. `scripts/audit/init_smoke.py` печатает ошибки, но не завершает процесс ненулевым кодом. Превратить результаты в явные проверки; заглушки natives не считать доказательством корректности движка.
6. **Инструкции расходятся с инструментами.** `wc3-lua-debug` предлагает `build` «или verify» после изменения исходников; `wc3-ai-brain` также не включает отдельную сборку перед verify. Сейчас verify ничего не пересобирает. В `scripts/README.md` остаются исторические трансформы, включая замену boolexpr голой функцией, которую текущие инструкции считают ошибкой. Отделить архивные миграции от поддерживаемых команд.

## Приоритеты реализации

| Очередь | Изменение | Практический результат |
|---|---|---|
| P0 | Исправить exit codes, маппинг, схему поиска и smoke assertions | Проверки действительно обнаруживают ошибки, диагностика указывает правильные исходники |
| P1 | Общий загрузчик manifest, конфигурация путей, `doctor` | Один источник путей и включённых секций, понятная диагностика окружения |
| P1 | `symbol`, `refs`, `context`, `--json`, `--limit`, `--max-lines` | Компактный ответ вместо чтения монолита и длинных результатов поиска |
| P1 | Пакетная инспекция объектов через существующий CLI | Меньше процессов и повторных обращений к данным Warcraft |
| P2 | Единый запуск аудиторов с baseline и проверкой новых находок | Снижение шума старых дефектов без сокрытия новых |
| P2 | Игровые сценарии с assertions и сбором артефактов | Повторяемая проверка рас, лобби, порталов и дипломатии |

Индекс символов должен учитывать manifest, определения `local F = function`, присваивания функций, ссылки и фактические границы функций. Обновлять кеш по содержимому; старый кеш не использовать молча. Для проверки изменённых участков учитывать зависимости; полный набор проверок сохранять перед выпуском.

## Скиллы

**Обновить существующие:** `wc3-tools` — достоверная диагностика и компактный поиск; `wc3-hivewe` — bulk, выбор полей, дерево технологий, preview изменений; `wc3-lua-debug` — привязка логов к конкретной сборке; `wc3-ai-brain` — явная последовательность build → verify → игровой сценарий.

**Добавить после реализации команд:**

- `wc3-change-check`: по типу изменения выбирает обязательные проверки, собирает результат и указывает ограничения. Не повторяет весь справочник архитектуры.
- `wc3-live-scenarios`: запускает именованные сценарии с ограничением времени, проверяет измеримые условия, собирает ошибки/логи. Общие fixtures для Lua-тестов и файловые сценарии вместо каждый раз сочиняемых строк Lua.

Скиллы про ассеты или релизы добавлять только при регулярной работе по этим направлениям. Каждый скилл должен ссылаться на небольшие тематические разделы, а не требовать читать весь комплект документации. Не обещать процент экономии токенов без измерения.

## HiveWE CLI: сначала использовать уже доступное

Установленная версия предоставляет `get-objects-bulk --fields`, `trace-unit`, `describe-race`, `batch-edit --dry-run`, `safe-move --dry-run`, `pathing-path --portals`, `regions-coverage`, `read-custom-map-data-log`. Python-обёртка использует только часть этих возможностей. Например:

```powershell
python scripts/wc3_hivewe.py raw get-objects-bulk --map F:/Gemini_23Race/map.w3x --type unit --ids h014,h05U --fields name,hp,ubui
```

Сначала добавить компактные адаптеры и сохранение полных JSON в артефакты. `race` сейчас показывает списки объектов, а не заявленное в скилле дерево обучения/исследований.

## Предлагаемые новые возможности HiveWE

Эти пункты требуют проверки и изменения отдельного исходного проекта HiveWE; наличие реализации в бинарнике не подтверждено.

1. **Версионированный JSON-контракт:** capabilities/schema, единые статусы и типы полей, ошибки с кодами, корректные exit codes. Контрактные тесты Python-обёртки против сохранённых ответов CLI.
2. **Структурный diff object data:** значения до/после, rawcode, поле, уровень, разрешённое имя WTS. Так бинарные изменения становятся проверяемыми при ревью.
3. **Пакет изменений как транзакция:** смешанные типы объектов и разные поля, проверка всех ссылок до записи, dry-run, журнал и восстановление. Это шире существующего batch-edit одного поля.
4. **validate-map:** ссылки train/build/research/abilities, типы объектов, WTS, импорты и пути моделей. Отчёт разделяет ошибки и предупреждения.
5. **Сценарии probe-map:** файл сценария, ожидание готовности моста вместо фиксированных задержек, assertions, session ID, хеш запускаемой сборки и итоговый отчёт. Защита от воспроизведения команд предыдущей сессии должна быть частью протокола.
6. **Дополнение pathing динамическими препятствиями:** размещённые деревья/ворота. Текущая справка CLI прямо сообщает, что их pathing пока не применяется; результат маршрута нельзя приравнивать к маршруту в живой игре.

Правила именно этой карты, например поля RegisterAiRace, оставить в Python-инструментах репозитория. Универсальные операции Warcraft и бинарных форматов развивать в HiveWE.

## Плагины и оценка эффекта

Пока новых внешних интеграций не предложено и ничего не установлено. Локальный MCP-сервер для HiveWE имеет смысл позднее: компактные типизированные инструменты object/bulk/diff/probe-report, общий кеш и стабильный контракт. До этого Python CLI проще поддерживать и тестировать.

Измерять на одинаковых задачах: число вызовов инструментов, объём выведенного текста, время до локализации ошибки, длительность проверок, число ложных «успехов» и повторных игровых запусков. Начать с трёх сценариев: ошибка callback со строкой, изменение параметра здания, исправление AI-расы.
