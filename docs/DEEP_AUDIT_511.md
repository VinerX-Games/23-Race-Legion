# Углублённая проверка семи коммитов 511

Проверка 2026-10-13. Область строго ограничена `9d80391`, `fb77906`, `fec12de`, `e9d9b62`, `e1eddf1`, `83d3fbf`, `4df89dd`. Коммит выпуска 510 используется только как база сравнения. Изменения после 511 не используются как кандидаты. Гипотеза скрытых объектов рассматривается наравне с ошибками инициализации, приказов, строительства и производства. Warcraft не запускался; игровая логика не исправлялась.

Полные diff и первоначальное описание каждого коммита: [COMMIT_AUDIT_510_511.md](COMMIT_AUDIT_510_511.md).

## Главный результат

Воспроизведены конкретные изменения поведения и дефекты 511, однако ни один пока не доказывает причину общей остановки наземных юнитов и отказа строительства. Новый прямой генератор объектов или команда общей блокировки в семи коммитах не найдены. Перенос инициализации также не дал новой Lua-ошибки в проверенном мок-сценарии.

Это более узкий вывод, чем «карта исправна»: мок-среда не воспроизводит native pathfinding, collision, размещение зданий, работу Warcraft с userdata или полную последовательность событий игры.

## Выполненные проверки

Проверочный скрипт: [audit_511_changes.py](../scripts/audit/audit_511_changes.py).

```powershell
python scripts/audit/audit_511_changes.py
```

Он читает исходники из Git-объектов, собирает Lua по manifest и не использует текущую рабочую карту в качестве сравниваемой версии. Из существующего `lobby_smoke` используется только настройка моков natives, без выполнения теста рабочей карты. Для точечных сценариев извлечены реальные тела функций через Lua AST.

## Подтверждённые дефекты и реальные изменения

### 1. Игнорируется `race.maxHeroes`: `e9d9b62`

Из `BrainProduce` удалены `heroMax`, суммирование существующих/заказанных героев и прекращение цикла по общей квоте. Лимиты конкретных типов остались, но ограничение количества героев расы больше не применяется.

В данных расы Драконов по-прежнему есть `maxHeroes=1` и комментарий, что пища сама по себе допускает второго дешёвого героя. Это не просто теоретический параметр: удалён код, который его применял. На реальном теле `BrainProduce` воспроизведено: при существующем первом герое 511 выдаёт заказ на другой тип, а 510 не выдаёт.

**Отношение к расследуемому багу:** может увеличить число обычных героев и их скопление возле алтарей. Не показан механизм остановки собственных рабочих в удалённых областях или появления невидимых преград. Это отдельная регрессия квоты, не установленный виновник pathfinding.

### 2. Несоответствие регистрации и обработчика цвета: `9d80391`

Новая подписка — `TriggerRegisterPlayerChatEvent(t, Player(i), "color", true)`. Exact match не пропускает строку `-colorred`. Сам обработчик после нормализации ищет `-colorred`, `-colorblue` и т. п.; точная строка `color` превращается в `-color`, которого в таблице нет.

Мок подтвердил, что прямой вызов нового обработчика со строкой `-colorred` цвет меняет, а регистрация рассчитана на другой текст. Прежние команды также имели испорченные пробелы; поэтому здесь не утверждается, что корректная команда работала в 510. Подтверждено, что новая регистрация несовместима со своим новым обработчиком.

**Отношение к багу:** нет цепочки до изменения движения, размещения или создания объектов.

### 3. Не обновляется локальный `ownerIndex`: `9d80391`

В новых `PercentGraph` и `ArmyExpGraph`:

```lua
local ownerIndex = MultiboardItemOwnerIndex[pi]
if ownerIndex == nil and EnsureMultiboardPlayerRow(pi) == nil then return end
-- ownerIndex остаётся прежним nil, даже если Ensure... создала строку
```

Дальше создание элемента таблицы требует `ownerIndex ~= nil`. Если `EnsureMultiboardPlayerRow` уже создала соответствующий column item, проблемы нет. Но если заголовок/column item ещё не готов, первая попытка обновления пропускается; следующий вызов перечитает index и сможет обновить. Точный сценарий воспроизведён на `PercentGraph`.

**Отношение к багу:** это локальный дефект таблицы UI, физические объекты и приказы не затрагиваются.

### 4. Изменяется выбор зданий и порядок производства: `e9d9b62`

`AiRunChooseBuildings` сортирует копию строк по rawcode. Состав взвешенного списка и число копий каждого варианта сохраняются; меняется соответствие случайного индекса конкретному зданию. Поэтому одинаковый случайный результат может дать другое строительство, а после этого отличаются состояние бота и последующие решения.

`AiFindProdBuilding` теперь выбирает максимальный HP% и использует координаты при равенстве. Военные unit types и production building types также обходятся в сортированном порядке. При ограничениях ресурсов и числа заказов это может менять, какие юниты реально производятся первыми.

**Отношение к багу:** это конкретный путь до других обычных зданий/юнитов, а не новый генератор blockers. Может объяснить другое скопление ботов и неудачное размещение, но не универсальную блокировку без дополнительной цепочки.

### 5. Добавленная сортировка `BrainBuild` не используется

В `BrainBuild` строится и сортируется `prodBuildingTypes`, после чего эта переменная больше не читается. Два прохода идут по `prodRows/otherRows`, заполненным в прежнем порядке `ipairs(buildOrder)`. Эта конкретная вставка **не меняет порядок строительных строк**. Не следует смешивать её с реально работающей сортировкой `AiRunChooseBuildings`.

## Перенос инициализации: `fec12de`

Перенесены 28 глобальных handles. Создание `Global_Hash/Timer/Temp*` выполняется первым шагом `Global___Init`; основные группы, силы, `Allmap` и таймеры — в `InitGlobals`. `main` сохраняет очередь, в которой `InitGlobals` предшествует `InitCustomTriggers` и `RunInitializationTriggers`.

Проверены функции между `Global___Init` и `InitGlobals`: инициализация SpellSleepAOE, SanctifiedEnchantment, boolexprs, bridge/chat, deferred UI, `Face2`, continent boolexprs. Не обнаружен новый прямой вызов изменённой группы для остановки/переноса всех юнитов в этой части. Создание исходных юнитов до очереди также сохранилось.

`FixEc` изменяет пересчёт экономики: без прежнего `b`, без мёртвых, с 24-м игроком. `FixEcEnum → AddCountDis → UpdateGraf` считает экономику и обновляет multiboard. В этой изменённой цепочке не найдено добавления/скрытия физического объекта или команды блокировки движения.

Создание группы, force, region, hashtable или timer не является созданием юнита/destructable. Однако новый порядок native allocations может иметь последствия, которые моки не моделируют. Поэтому коммит остаётся кандидатом для изоляции общего стартового состояния, **но его высокий приоритет ранее был основан на широте изменения, не на обнаруженной причинной цепочке**.

## Итог для поиска причины в этих семи коммитах

1. **Конкретные изменения физического мира через старые механизмы** лучше всего прослеживаются из `e9d9b62`: другие выбранные здания, другой порядок производства, отсутствие общей квоты героев. Связь с массовой остановкой не доказана.
2. **Общее стартовое состояние** наиболее существенно меняет `fec12de`. Проверки не обнаружили новой ошибки очереди или добавленного объекта в `main`, но не проверяют реальный engine pathfinding.
3. `9d80391` и `e1eddf1` в основном затрагивают экономический UI; обнаруженные UI-дефекты сами не объясняют красные клетки строительства. `fb77906` меняет roster/лимиты героев HordeW2. Для них не показана более сильная связь с общей остановкой.
4. `83d3fbf` вводит предыдущие изменения в исполняемый script; `4df89dd` меняет номер версии. Независимого механизма сбоя в них нет.

На основании этих проверок нельзя добросовестно назвать конкретную строку причиной остановки. Гипотеза невидимых объектов не подтверждена и не использовалась как предпосылка. Сужение до этих семи коммитов сохраняется: неопределённость относится к их косвенным последствиям и engine-поведению, а не к переносу поиска на поздние правки.
