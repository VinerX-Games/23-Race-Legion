# Дизайн: осмысленный ИИ-«мозг» армии (objective + отряды)

Статус: **черновик на ревью**. Кода нет. Опирается на уже сделанный
data-driven рефактор (`81_ai.lua` реестр + движки) и существующие структуры.

Связанные доки: [AI_REFACTOR_PLAN.md](AI_REFACTOR_PLAN.md) (фазы 1–3, реестр),
[HANDOFF_AI_PHASE3.md](HANDOFF_AI_PHASE3.md) (мост, тестирование).

---

## 1. Цель

Заменить текущую петлю атаки (stateless swarm) на **осмысленное поведение
уровня армии** для карты жанра Risk: сотни юнитов, много нейтральных зданий под
захват, выраженные фронты, ТП-маги как логистика, герои, оборона столиц.

Желаемое поведение (приоритеты из обсуждения):
1. **Фокус силы** — концентрировать армию на выбранной цели, не распыляться.
2. **Отряды ~12** объединяются в армии, ходят/коммитятся вместе (не скармливаются
   по одному).
3. **Оборона** — держать резерв у столицы, возвращать армию при атаке на неё.
4. **Логистика** — использовать ТП-магов для переброски отрядов к фронту/цели.
5. (Желательно) учёт перевеса сил — не лезть туда, где явно слабее.

Режим выбирается **per-bot** через реестр (`brain="objective"` / `"swarm"`),
старый рой остаётся фоллбэком и эталоном для A/B-сравнения в той же игре.

## 2. Диагноз текущей петли (что меняем)

`TryAttack()` ([_ai/94_ai_attack.lua](map.w3x/_lua/monolith_split/sections/80_runtime/_ai/94_ai_attack.lua)),
вызывается из `PlayerArmy` по таймеру для AiMass случайных юнитов:

> из точки одного юнита → enum врагов в расширяющемся радиусе → цель = столица/
> **случайный** враг → собрать незанятых соседей (≤12) во временную группу →
> `attack` на точку. Блоб распадается на следующем тике.

Два корня проблемы — **один и тот же**: решение принимается из локального взгляда
одного юнита, поэтому (а) нет общей картины → нет стратегии, (б) дорогой
`GroupEnum`/`ProcessContinentalStuff` крутится на каждого юнита каждый тик
(в «широком» режиме — до 9 проходов по карте на юнита).

**Принцип решения:** ввести **общую модель мира на игрока, считаемую редко**
(sensing централизован → дёшево и «умно»), а действие юнита/отряда сделать
**дешёвым чтением** готового решения.

## 4. Архитектура: три слоя

```
            ┌──────────────────────────────────────────────┐
   медленно │  PERCEIVE (AiPerceive)  — 1 проход на игрока  │  раз в ~2–4 c
   (sense)  │  строит/обновляет World Model в AiData[pi]    │
            └───────────────┬──────────────────────────────┘
                            │ читает
            ┌───────────────▼──────────────────────────────┐
   средне   │  PLAN (AiPlanArmy) — раздаёт отрядам цели     │  раз в ~1–2 c
   (decide) │  ранжирует objectives, назначает squads       │
            └───────────────┬──────────────────────────────┘
                            │ читает приказ отряда
            ┌───────────────▼──────────────────────────────┐
   часто    │  ACT (AiSquadTick) — отряд исполняет FSM:     │  текущий темп
   (act)    │  march / muster / engage / retreat / port     │  PlayerArmy
            └──────────────────────────────────────────────┘
```

Бюджет: дорогой sensing — реже всего и **по одному игроку за тик** (round-robin,
как уже сделано в `PereborPlayerForArmy` через `BotsActive`). Act дёшев — только
чтение + 1–2 ордера на отряд.

## 5. World Model (что кладём в `AiData[pi]`)

Считается в `AiPerceive(pi)` одним проходом, переживает между тиками:

```lua
AiData[pi].wm = {
  tick        = <счётчик>,
  capitalHP   = <текущее ХП своей столицы / %>,   -- для триггера обороны
  threatHome  = <сумм. сила врага в радиусе R вокруг playerCapital[pi]>,
  armyCount   = <живых в udg_Ai_army[pi]>,
  armyCentroid= {x,y},                              -- центр масс армии
  objectives  = { {u=<unit|nil>, x,y, kind, score, claimedBy=<squadId|nil>}, ... },
  fronts      = { {x,y, ourPow, enemyPow}, ... },   -- опц. (вариант C-lite)
}
```

### Источники целей (`objectives`) — специфика Risk
**Decentralized:** сотни юнитов и зданий, поэтому **не скорим по ХП отдельного
юнита** (ХП важно только для столицы). Мыслим **кластерами полезных зданий
врага** — узлами производства и инкома. Цель = область, а не одиночный юнит.

- **Кластер инфраструктуры врага** (главное): сгусток вражеских зданий
  производства/инкома. `kind="cluster"`. Ценность ∝ суммарной «полезности» зданий
  в радиусе (см. `clusterValue` ниже), а не их ХП.
- **Захват нейтралки**: `udg_ZahvatBuildings`, не наши, в досягаемости —
  массовый пул, тоже агрегируем в кластеры. `kind="capture"`.
- **Вражеские столицы**: `udg_StolicaGroups` ∧ враг. `kind="capital"` — **только
  здесь** учитываем ХП/осаду (это решающая точка). Высокий базовый вес.
- **Фронт**: отложено (см. §11).

### Ценность кластера
Зданиям задаём «полезность» данными (а не по ХП):
```lua
AiBuildingValue = {                 -- глобальная таблица + расовые оверрайды
  -- [buildingTypeId] = value      производство/инком/ключевые > рядовые
}
clusterValue(x,y) = Σ AiBuildingValue[id] для вражеских зданий в R_cluster
```
Узлы кластеров находим **сеточно** (бакеты по координатам в один проход), а не
попарным сравнением сотен зданий — дёшево и устойчиво к плотности карты.

### Скоринг цели (данные — в реестре расы/глобально)
```
score = w_kind[kind] * kindBase
      + w_value * clusterValue(target)              -- ценнее узел — выше
      - w_dist  * dist(armyCentroid, target)        -- ближе лучше
      - w_claim * claimedSize                       -- уже назначено сил → ниже
   (+ w_siege * capitalSiege  только для kind="capital")
```
Веса `w_*`, `kindBase`, `R_cluster` — поля
`RegisterAiRace(..., brainWeights={...})` с глобальным дефолтом. «Осмысленность» =
данные. ХП юнита из формулы исключён намеренно.

**Много целей (≈50 зданий/континент):** держим **top-K** (параметр `topK`,
дефолт задаём, тюним позже) одиночным проходом со вставкой в фикс-буфер; пул
кластеров пересобираем раз в `clusterEvery` тиков (ленивое устаревание).

## 6. Отряды (squads) и армии

### Сущность
```lua
AiSquads[pi] = { [squadId] = {
  members   = <group>,        -- юниты отряда (cap ~12)
  state      = "muster"|"march"|"engage"|"retreat"|"port",
  objective  = <ссылка в wm.objectives | nil>,
  rally      = {x,y},          -- точка сбора/коммита
  size       = <живых>,
  role       = "assault"|"defense",  -- defense = из/для AiCapitalGuard
}, ... }
```

### Формирование
- Новый боевой юнит (`aiUnitJoinsArmy`) **не идёт в общий котёл**, а
  приписывается к **ближайшему по centroid отряду роли assault** с `size<cap`;
  если таких нет — создаётся новый отряд в статусе `muster` у текущего rally
  (по умолчанию — у `playerCapital[pi]` или передовой захваченной точки).
- Оборонный резерв (`role="defense"`) наполняется как сейчас через
  `aiUnitJoinsCapitalGuard` (лимит ~`Number/5` уже есть) — переиспользуем 1:1,
  просто оборачиваем в squad-обёртку.

### FSM отряда (`AiSquadTick`, дёшево)
```
muster:  ждать size >= commitMin (напр. 8). Стянуть членов к rally.
         size>=commitMin → взять top objective (claim) → state=march.
march:   двигаться к objective.xy. Если есть ТП-маг и далеко → state=port.
         Дошли (dist<eps) или встретили врага → state=engage.
engage:  attack на objective / врагов вокруг. Если objective мёртв →
         перевыбрать цель (вернуться к march). Если потери > X% или
         threatHome подскочил → state=retreat.
retreat: отойти к playerCapital[pi] / ближайшей своей точке. Долечились/
         подкрепились → muster.
port:    запросить переброску (RequestPort/MakeTPMage) к rally цели → march.
```

Эта же машина решает «армия ходит строем»: муштра до `commitMin`, затем
коллективный коммит, а не скармливание по одному.

### Концентрация силы (крупные цели)
Под столицу/жирный кластер заруба может быть на сотни юнитов — **нельзя слать по
12 и сливать**. Решаем требуемой массой на цель:
```
target.demand = clamp(k_demand * (enemyPowAround(target) или kindBase), min, max)
```
- Один отряд **не коммитится**, пока суммарный `size` отрядов, заклеймивших цель,
  не достигнет `demand`. До этого `muster` у общего `rally` цели.
- Несколько отрядов могут клеймить одну цель (claim — не эксклюзив, а вклад в
  набор `demand`). Альтернатива «увеличить отряд» — частный случай: `squadCap`
  растёт под `demand`. Параметризуем оба, дефолты ставим, сравним.
- Мелкая нейтралка (`demand` мал) — забирается одним отрядом без накопления.

### Оборона (приоритет 3)
- В `AiPerceive`: если `threatHome` высок ИЛИ `capitalHP` падает →
  выставить флаг `wm.defendHome=true`.
- В `AiPlanArmy`: при `defendHome` — ближайший(е) assault-отряд(ы)
  переводятся в `retreat`→к столице; defense-резерв уже там. Сняв осаду —
  флаг гаснет, отряды возвращаются к objective.

### Логистика ТП (приоритет 4)
- ТП-маги уже копятся в `AiUnitsToPort[pi]`; `PortTo`/`MakeTPMage` умеют
  телепорт к юниту. Новое: `port`-состояние отряда вызывает существующую
  переброску к `rally` цели вместо случайного `RequestPort`. ТП экономит проход
  через всю карту → ключ к фокусу силы на дальней цели.
- Герои: помечать в отряде; держать рядом с телом отряда (не убегать в одиночку),
  кастовать через существующий `AiRunAttacker`. Доп. правило: герой не остаётся
  один (если `size<2` вокруг героя → retreat).

## 7. Расписание тиков (без спайков)

Раскидать по уже существующим таймерам round-robin (один игрок за тик):
- `AiPerceive(pi)` — на таймере `PereborPlayerForArmy`-класса, **1 игрок/тик**.
- `AiPlanArmy(pi)` — следом, тоже 1 игрок/тик (читает свежую wm).
- `AiSquadTick` — в существующем `PlayerArmy`-цикле, но вместо AiMass случайных
  юнитов → итерируем отряды игрока (их единицы–десятки, не сотни).

Это **снижает** нагрузку относительно текущего (сейчас: AiMass·дорогой sensing;
станет: 1 sensing + дешёвый act по отрядам).

## 9. Псевдокод ключевого (эскиз, не финал)

```lua
-- медленно, 1 игрок/тик
function AiPerceive(pi)
  local wm = AiData[pi].wm or {}; AiData[pi].wm = wm
  wm.armyCentroid, wm.armyCount = GroupCentroid(udg_Ai_army[pi])
  wm.threatHome = EnemyPowerAround(playerCapital[pi], R_HOME)   -- 1 enum
  wm.capitalHP  = playerCapital[pi] and GetUnitState(...LIFE) or 0
  wm.defendHome = wm.threatHome > guardPow(pi) or capitalUnderAttack(pi)
  CollectObjectivesTopK(pi, wm)   -- 1 проход: захват/столицы/слабые, top-K
end

-- средне, 1 игрок/тик
function AiPlanArmy(pi)
  local wm = AiData[pi].wm; if not wm then return end
  ReapDeadSquads(pi)
  if wm.defendHome then return RecallToHome(pi) end
  for _, sq in pairs(AiSquads[pi]) do
    if sq.state=="muster" and sq.size>=commitMin(pi) then
      sq.objective = PickBestUnclaimed(wm.objectives, sq)  -- скоринг §5
      if sq.objective then sq.objective.claimedBy=sq; sq.state="march" end
    end
  end
end

-- часто, в PlayerArmy
function AiSquadTick(pi, sq) ... end   -- FSM из §6, дешёвые ордера
```

(`GroupCentroid`, `EnemyPowerAround`, `CollectObjectivesTopK` — новые мелкие
хелперы; `EnemyPowerAround` = взвеш. сумма по `GetUnitGoldCost`/типу в 1 enum.)

## 10. Миграция, фоллбэк, тестирование

1. **Слой данных без поведения**: ввести `AiSquads`, `AiData[pi].wm`,
   формирование отрядов в `aiUnitJoinsArmy` (за флагом — пока no-op для swarm).
2. **`brain="objective"` на 1 расе** (Horde или JT). Старый путь не трогаем.
3. Обкатка **живым мостом** без перезапуска (`agent_bridge.py`, см. HANDOFF):
   спавн бота, `exec` для чтения `AiData[pi].wm`, гистограмма ордеров армии,
   горячее переопределение функций для подбора весов.
4. Тюнинг `brainWeights` → визуально: фокусится ли, копит ли отряд, возвращается
   ли на оборону, юзает ли ТП.
5. По одной расе включать `brain="objective"`; swarm остаётся для несведённых.

Канон сборки прежний: правки в `sections/**` → `python build_map_lua.py` →
`luaparser` parse → мост. Никаких правок собранного `war3map.lua`.

## 11. Решения и параметры (зафиксировано)

- **Скоринг**: по кластерам зданий (производство/инком), НЕ по ХП юнита. ХП —
  только для `kind="capital"`. → §5.
- **Top-K / частота**: всё параметризуем (`topK`, `clusterEvery`, `R_cluster`),
  ставим дефолты, сравниваем мостом позже. Ориентир — ≈50 зданий/континент.
- **Скоринг глобальный + расовые оверрайды** (один дефолт, точечные правки).
- **Фронты — отложены** (непонятно правильное применение; вернёмся после v1).
- **Крупные цели**: концентрация силы через `demand` (несколько отрядов на цель
  и/или растущий `squadCap`) — не слать по 12 на зарубу в 200. → §6.
- **Всё тюнингуемое — поля `brainWeights`** с глобал-дефолтами.

### Технический рефактор (попутно, инкрементально)
Старый код костыльный: состояние раскидано по глобалкам (`gUnit`, `gX`, `Counter`,
`gEnemyGroup`, `EnemyCapital`…), функции общаются через них, а не через параметры.
Новый brain-код пишем **на локалках и передаче параметров** (`AiPerceive(pi)`,
`AiSquadTick(pi, sq)` — чистые входы, состояние только в `AiData[pi]`/`AiSquads`).
Существующие глобалки трогаем точечно при миграции конкретного пути; массовую
расчистку — отдельным проходом, не блокируя brain. (Перф-плюс: меньше глобал-
лукапов в горячем цикле.)

## 12. Производство и развитие (отдельный трек)

Не часть army-brain, но та же болезнь — рандом. Два узких места:

### 12.1 Размещение зданий (вместо рандома)
Сейчас `TryBuild` ([_ai/98_ai_build.lua](map.w3x/_lua/monolith_split/sections/80_runtime/_ai/98_ai_build.lua))
кидает здание в случайную точку по кольцу `AiBuildingRadius` от рабочего, до 12
случайных попыток на воду/стены. Это даёт разбросанную, дырявую застройку.

Цель — **детерминированный поиск места** вокруг якоря (столица/ратуша):
```
AiPlaceBuilding(pi, builder, buildId):
  anchor = ближайшая своя ратуша/столица (или текущая позиция)
  для r в [r0, r0+step, ...]:           -- расширяющиеся кольца
    для угла в фикс. наборе (напр. 8–12 секторов, со сдвигом фазы):
      (x,y) = anchor + r*dir(угол)
      если CanPlace(buildId,x,y) и не слишком близко к др. зданиям:
        return (x,y)                     -- первое валидное, ближайшее к якорю
  fallback → старый рандом
```
- `CanPlace` = существующие `IsTerrainPathable`/`RectContains*`-проверки.
- «Не слишком близко» — дешёвый enum своих зданий в малом радиусе (или сеточный
  бакет занятых точек на игрока в `AiData[pi]`).
- Спец-случаи (стены/порты у воды) — оставить как ветки, но тоже детерминированно.
- **Кучнее, ближе к базе, меньше дыр.** Параметры (`r0`, `step`, секторов,
  min-spacing) — данные с дефолтами.

### 12.2 Заказ юнитов (вместо взвешенного рандома)
Сейчас `AiRunProduction` ([81_ai.lua](map.w3x/_lua/monolith_split/sections/81_ai.lua))
кладёт в `tArray` по `weight` копий и берёт `GetRandomInt`. Это «состав по матожиданию»,
но реактивности ноль — не подстраивается под нехватку/контру.

Идеи (от простого к сложному; выбрать на ревью):
1. **Целевые пропорции** вместо весов-в-рандом: для каждого юнита расы задан
   желаемый % в армии (`compTarget`). Берём юнита с наибольшим
   `compTarget[id] - текущаяДоля(id)` — тянем состав к цели детерминированно.
   Состав армии уже считается в World Model (§5) — переиспользуем.
2. **Реакция на угрозу/перевес**: при `defendHome` — смещение к дешёвым/быстрым;
   при наличии вражеских летающих/осадных — буст контр-юнитов (теги на юните
   данными: `tags={"anti_air","siege"}`, контр-правила).
3. Бюджет/тайминги оставить как есть (`Strateg` уже даёт ресурсы по `i`).

Минимальный шаг — п.1 (data-driven `compTarget`, фоллбэк на текущий рандом).

## 13. Флот и десант (морская логистика)

Флот — **параллельная система**: `PlayerNavy`→`TryAttackN`
([_ai/95_ai_attack_naval.lua](map.w3x/_lua/monolith_split/sections/80_runtime/_ai/95_ai_attack_naval.lua)),
пул `udg_Ai_navy[pi]`, постройка верфей через `AiDispatchNaval`/`aiNavalTrain_*`,
цели — water-related враги (`f_EnemyUnitN`: `CityNearWater`/`Navy`/`Port`).
Сейчас флот живёт сам по себе и бьёт морские цели; сухопутный brain его не знает.

### Текущая переброска через берег
ИИ (как игроки) телепортит армию через **захваченные прибрежные города**
(`MakeTPMage`/`PortTo`, `AiUnitsToPort`). Дёшево и быстро, но: (а) нужен свой/
захваченный прибрежный город рядом с целью; (б) если берег цели плотно обороняют —
ТП высаживает прямо под удар.

### Что добавляем — десант (transport landing)
Третий способ доставки отряда к цели за водой, **альтернатива ТП** когда ТП не
проходит:
- триггеры выбора `port`-режима отряда (§6) расширяем: `tp` (через город) vs
  `landing` (через транспорт). `landing` выбирается если у цели нет годной ТП-точки
  ИЛИ берег цели сильно обороняется (дешёвый enum силы у предполагаемой ТП-высадки).
- **Поток `landing`**: squad идёт к ближайшей своей пристани → грузится в транспорт
  (тип транспорта — поле расы `transport=FourCC(...)`, как уже есть `naval`/`wall`)
  → транспорт плывёт к точке высадки у цели → выгрузка → squad→`engage`.
- Точки высадки: переиспользуем водные move-точки `GoToWaterPoint`
  ([_ai/97_ai_water.lua](map.w3x/_lua/monolith_split/sections/80_runtime/_ai/97_ai_water.lua))
  и `udg_CityNearWater` как кандидаты берега; для пробоя — высадка рядом с целью,
  а не в своём городе.
- Флот **прикрывает десант**: при активном `landing`-отряде ближайшие navy-юниты
  получают цель = маршрут транспорта (сопровождение). Это первая связка sea↔land.

### Параметризация (данные расы)
```lua
RegisterAiRace(..., {
  transport   = FourCC('...'),   -- тип транспорта (грузовой)
  transportCap= 6,               -- мест (юнитов в отряде на борт)
  landingWhen = { tpBlockedPow=<порог силы у ТП-точки>, needCoastalCity=true },
})
```
Если у расы нет `transport` — `landing` недоступен, остаётся только `tp`/пеший
(текущее поведение = фоллбэк).

### Фаза
- **М1** — десант одного отряда: пристань→погрузка→плавание→высадка→engage, выбор
  `tp` vs `landing` по простому правилу. Обкатка мостом на 1 расе с флотом
  (BloodElves/Naga/Horde — у них есть `naval`).
- **М2** — сопровождение флотом + выбор точки высадки для пробоя обороны.
